# Deploying to Render

The blueprint in `render.yaml` creates three things: the Next.js site,
the FastAPI service and a PostgreSQL database, all in Singapore.

Expect about **$21/month** — roughly $7 for each web service and $7 for
the database. The free tiers are not used: free web services sleep after
15 minutes, so a client clicking a portal link would wait around a
minute for it to wake, and free databases are deleted after 30 days.

---

## 1. Push the branch and merge

The blueprint deploys from `main`.

```bash
git push -u origin feat/client-portal
# open the PR, merge it, or merge locally:
#   git checkout main && git merge feat/client-portal && git push
```

## 2. Create the services

Render dashboard → **New** → **Blueprint** → pick `Zyora-Dev/mikan-groups`.

Render reads `render.yaml` and creates `mikan-db`, `mikan-api` and
`mikan-web`. It will ask for three values it cannot work out by itself.
Leave them blank for now — the API's URL does not exist until it has
been created — and set them in step 3.

The first build of `mikan-api` will fail its health check. That is
expected: `WEB_BASE_URL` is still empty and the app refuses to start
without it. Step 3 fixes that.

## 3. Set the three manual values

Once both services exist, copy their URLs from the dashboard. They look
like `https://mikan-web-xxxx.onrender.com`.

On **mikan-api** → Environment:

| Key | Value |
|---|---|
| `WEB_BASE_URL` | the **web** URL, no trailing slash |
| `CORS_ORIGINS` | the **web** URL, no trailing slash |

On **mikan-web** → Environment:

| Key | Value |
|---|---|
| `NEXT_PUBLIC_API_BASE` | the **api** URL + `/api/v1` |

For example:

```
WEB_BASE_URL         = https://mikan-web-xxxx.onrender.com
CORS_ORIGINS         = https://mikan-web-xxxx.onrender.com
NEXT_PUBLIC_API_BASE = https://mikan-api-xxxx.onrender.com/api/v1
```

Three things that will cost you an afternoon if missed:

- **No trailing slash.** `CORS_ORIGINS` is compared to the browser's
  `Origin` header exactly; a trailing slash never matches and every
  request fails with no useful error.
- `NEXT_PUBLIC_API_BASE` is baked into the JavaScript bundle at build
  time, so **mikan-web must be redeployed** after setting it. Changing
  it without a rebuild does nothing.
- `JWT_SECRET` is generated by Render. Do not replace it — doing so
  signs everyone out.

Redeploy both services after saving.

## 4. Move the data

The database starts empty. This copies everything from your machine.

```bash
# Render → mikan-db → Connect → External Database URL. Quote it.
./scripts/migrate-to-render.sh 'postgresql://mikan:...@singapore-postgres.render.com/mikan_groups'
```

It dumps, restores and then prints a row count per table so you can
check nothing was dropped. Safe to re-run — the restore replaces rather
than duplicates.

The dump carries `alembic_version`, so the API will not try to re-run
migrations that are already applied.

**Uploaded files are not in the database dump** — only their paths are.
Copy the files separately, or every attachment will point at something
that is not there:

```bash
brew install render && render login
./scripts/upload-files-to-render.sh srv-xxxxx    # the mikan-api service id
```

## 5. Check it works

```bash
curl https://mikan-api-xxxx.onrender.com/health
# {"status":"ok","environment":"production"}
```

Then, in a browser:

- the public site loads
- `/portal` signs in as a client and shows their projects
- `/internal/erp/team/login` signs in as admin
- **Forgot password** sends a real email with a link to the live site,
  not to localhost
- a client cannot reach `/internal/erp/team` and is redirected

## 6. Custom domain

Render → mikan-web → Settings → Custom Domain → add `mikan-groups.com`,
then add the CNAME it gives you at your registrar.

Afterwards, update `WEB_BASE_URL` and `CORS_ORIGINS` on **mikan-api** to
the real domain and redeploy, or reset emails will keep pointing at the
`onrender.com` address.

## Things to know

**Email.** Reset links and notifications go through Zoho ZeptoMail, and
the credentials live in the database rather than the environment — set
them at `/internal/erp/team/settings`. Until they are set, password
resets are generated and recorded but never delivered.

**Uploads.** `mikan-api` has a 10 GB disk mounted at `/var/data/uploads`.
A disk pins the service to a single instance, so scaling to more than
one means moving to S3 first. `storage.py` is written to make that a
two-function change.

**Rate limiting** counts in process memory. With one instance that is
exact. Behind several, the effective limit multiplies by the instance
count — the per-account lockout is still the real protection.

**Backups.** The `basic-256mb` plan takes daily backups with 7-day
retention, under mikan-db → Recovery. Free plans have none, which is
part of why the blueprint does not use one.

**Region.** Everything is in Singapore and the database must stay in the
same region as the API; splitting them adds latency to every query.
